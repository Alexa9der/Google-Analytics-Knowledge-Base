# Architecture Decisions

## Purpose

This document records durable repository decisions and their rationale. It is intentionally lightweight: use it for choices that future contributors or agents might otherwise reverse accidentally.

## ADR-001 — Separate Evidence from Facts

**Status:** Accepted

**Decision:** Source provenance is stored in Evidence records; atomic claims are stored in Fact records.

**Rationale:**

- one source can support multiple claims;
- one claim can use multiple sources;
- provenance and semantics change independently;
- verification remains explicit and machine-readable.

**Consequence:** Evidence does not own reverse Fact lists. Facts reference Evidence.

## ADR-002 — Facts are atomic

**Status:** Accepted

**Decision:** Each Fact represents one independently verifiable claim.

**Rationale:** Atomic Facts can be updated, scoped, reused, and contradicted independently.

**Consequence:** Combined limits, permissions, delays, and recommendations must be split when they can change independently.

## ADR-003 — Concepts are service-independent where possible

**Status:** Accepted

**Decision:** Concepts define reusable meaning rather than repeating product-specific behavior.

**Rationale:** Shared terminology reduces duplication across Google services and improves cross-service analysis.

**Consequence:** Mutable product limits belong in Facts, not Concepts.

## ADR-004 — Services own identity and boundaries only

**Status:** Accepted

**Decision:** Service records describe product identity and high-level analytical role.

**Rationale:** Copying detailed behavior into Service records would create multiple competing sources of truth.

**Consequence:** Detailed product behavior remains in Facts.

## ADR-005 — Views and Reports are non-canonical projections

**Status:** Accepted

**Decision:** Views and Reports organize and synthesize canonical entities but do not own current truth.

**Rationale:** Narrative documents are useful for humans and agents but are harder to update atomically and verify mechanically.

**Consequence:** Important claims must exist as Facts before appearing in projections.

## ADR-006 — INDEX.jsonl is generated

**Status:** Accepted

**Decision:** `INDEX.jsonl` is generated from canonical and validated projection files.

**Rationale:** A generated locator prevents manual drift and supports low-token entity lookup.

**Consequence:** Manual edits are prohibited. Canonical sources must be changed and the generator rerun.

## ADR-007 — Typed ULID identifiers are stable identity

**Status:** Accepted

**Decision:** Entities use `<TYPE>-<ULID>` identifiers generated by repository tooling.

**Rationale:** IDs remain globally unique, sortable, path-independent, and safe across package refactors.

**Consequence:** Paths and slugs are not identity. Handcrafted sequential IDs are invalid practice.

## ADR-008 — Official Evidence is required for confirmed product Facts

**Status:** Accepted

**Decision:** A confirmed Fact about Google product behavior requires official first-party Evidence whenever available.

**Rationale:** The project aims to be authoritative and auditable, not a collection of remembered or AI-generated claims.

**Consequence:** AI output, unsupported observation, and third-party summaries cannot independently confirm a Fact.

## ADR-009 — Context loading is index-first

**Status:** Accepted

**Decision:** Agents should use `STATE.md` and `INDEX.jsonl` before scanning packages.

**Rationale:** The repository is large; broad scans waste tokens and increase accidental cross-scope edits.

**Consequence:** Normal work uses narrow graph traversal and relevant Views.

## ADR-010 — Full validation is required before merge

**Status:** Accepted

**Decision:** Schema, link, front matter, index freshness, tests, Ruff, and mypy must pass before merge.

**Rationale:** Repository integrity depends on multiple layers that no single validator covers.

**Consequence:** Temporary bypasses must be removed before PR readiness.

## ADR-011 — One coherent branch and PR per phase or maintenance task

**Status:** Accepted

**Decision:** Research phases and coherent maintenance tasks use dedicated branches and Pull Requests.

**Rationale:** This provides reviewable scope, CI isolation, rollback clarity, and understandable history.

**Consequence:** Unrelated refactors must not be mixed into research PRs.

## ADR-012 — STATE.md is operational, ROADMAP.md is strategic

**Status:** Accepted

**Decision:** `STATE.md` records current execution; `ROADMAP.md` records completed and candidate strategic phases.

**Rationale:** Mixing current task state with future ideas causes autonomous agents to start unapproved work.

**Consequence:** Roadmap candidates require explicit activation in `STATE.md`.

## ADR-013 — Repository state replaces conversation memory

**Status:** Accepted

**Decision:** Durable context must be written into repository files, PRs, and commits rather than depending on chat history.

**Rationale:** Future agents may have no access to previous conversations.

**Consequence:** Every session ends with an explicit repository-visible handoff.

## ADR-014 — Production inventory tests are intentional contracts

**Status:** Accepted

**Decision:** Tests that assert entity counts are updated only when production inventory changes intentionally.

**Rationale:** They detect missing, duplicated, or unexpectedly indexed entities.

**Consequence:** Count updates must accompany reviewed entity additions or removals, not conceal generator errors.

## Changing a decision

To replace an accepted decision:

1. Add a new ADR entry.
2. Mark the previous decision superseded.
3. Explain migration and compatibility impact.
4. Update architecture, workflow, schemas, tests, and agent guidance as needed.
5. Validate the repository through a dedicated PR.
