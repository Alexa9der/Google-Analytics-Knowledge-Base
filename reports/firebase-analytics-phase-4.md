# Summary

Phase 4 establishes Firebase Analytics as the app-side collection and integration layer in the wider
Google Analytics system. It closes the route from first app launch through sessions, engagement,
screens, custom events, key events, purchases, attribution, AdMob impression revenue, and event-level
BigQuery export.

# Core app lifecycle

```text
Google Play install observation
→ first launch after installation or reinstallation
→ first_open
→ session_start
→ user_engagement and screen_view
→ app events and key events
```

An app download does not trigger `first_open`. This is the canonical break between a store-side
install observation and an analytics event created after launch.

# Event model

The SDK automatically collects some events and user properties and permits custom events. An event
represents an application occurrence, not a user, device, or session. Event names are case-sensitive.
Custom parameters are exported to BigQuery, but registration as a custom dimension or metric is
required for standard-report visibility.

# Sessions and engagement

`session_start` creates the session context and automatically associates `ga_session_id` and
`ga_session_number` with events. `user_engagement` and `screen_view` have independent trigger rules
and must not be treated as session counts.

# Identity and user properties

`user_id` is optional, applies prospectively, and must not contain directly identifying information.
`user_pseudo_id` is generated automatically for the app-on-device context and is present at event
grain in BigQuery. A project can define up to 25 case-sensitive custom user properties.

# Audiences and key events

Audiences can use device data, events, and user properties. Any collected event can be marked as a
key event. Standard properties support up to 30 marked key events. Applicable app streams mark
`first_open`, `in_app_purchase`, and documented subscription lifecycle events as key events by
default. Marking is prospective and can take up to 24 hours to appear in standard reports.

# Attribution

Source, medium, and campaign dimensions exist at user, session, and event scopes. A session is
associated with one campaign or traffic source, and encountering a new source during a session does
not start another session. Attribution assigns credit for key events to eligible touchpoints within
the configured lookback window.

# Purchases and subscriptions

`in_app_purchase` covers completed store-processed purchases and initial subscriptions. Android
purchase data requires a Google Play link. Analytics revenue can differ from Google Play Console,
and overlapping automatic and manual tracking can create duplicates.

# AdMob integration

Firebase linkage and Analytics SDK integration enable AdMob user metrics. Impression-level ad
revenue can flow into Google Analytics for Firebase. The impression-level callback remains distinct
from mutable AdMob estimated earnings and finalized payment.

# Collection and consent boundary

Analytics collection can be disabled and later enabled programmatically, with runtime state
persisting across app executions. Measurement collection and ad-personalization eligibility are
separate controls.

# BigQuery export

Firebase supports daily BigQuery synchronization for Analytics and selected Firebase products.
Initial propagation can take up to 48 hours. Standard Analytics export is limited to one million
events per day, while Analytics 360 is exempt from that standard limit. Unlinking stops future
population; already exported data remains subject to BigQuery retention and billing.

# Measurement boundary

Firebase Analytics directly covers application-side collection and the Firebase integration surface.
It does not replace Google Play store statistics, Search Console search analytics, AdMob financial
settlement, or the broader GA4 property and reporting model.

# Key distinctions

- install observation ≠ `first_open`;
- `first_open` ≠ `session_start`;
- session ≠ event ≠ user;
- `user_id` ≠ `user_pseudo_id`;
- event ≠ key event;
- user-scoped source ≠ session-scoped source ≠ event-scoped source;
- Analytics purchase revenue ≠ Google Play financial reporting;
- impression-level ad revenue ≠ finalized AdMob payment;
- collection consent ≠ ad-personalization eligibility;
- Firebase console report ≠ BigQuery event export.

# Coverage

Fully covered for the project objective: core app lifecycle, events, sessions, engagement, screens,
identity, user properties, audiences, key events, app attribution, Google Play purchase linkage,
AdMob impression revenue, collection controls, and BigQuery export boundaries.

Excluded from detailed research because they do not block the attribution objective: Crashlytics,
Performance Monitoring, Remote Config, A/B Testing, and Cloud Messaging. Their existence as optional
BigQuery export sources is recorded without separate product analysis.

# Open questions

- exact app campaign attribution behavior for every deep-link and deferred-deep-link path;
- exact consent-state effect on event completeness and attribution in each jurisdiction;
- full daily versus streaming Analytics export schema behavior;
- cross-device identity behavior when `user_id` is absent or changes;
- exact reconciliation between impression-level revenue, AdMob reports, and finalized payment;
- practical preservation of `/fb` source data through website, Play Store, and first open.

# Next phase

Phase 5 should research Google Analytics 4 as the property, data-stream, reporting, API,
Measurement Protocol, retention, thresholding, consent, attribution, and cross-platform layer. It
must reuse the Firebase event model established here rather than duplicating it.
