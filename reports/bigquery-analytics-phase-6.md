# Summary

Phase 6 establishes BigQuery as the governed warehouse and transformation boundary for the Google
analytics ecosystem. The research covers the platform hierarchy, GA4 export lifecycle and schema,
canonical SQL reconstruction, retention and recovery, performance controls, transformation surfaces
and access governance.

# Official sources

Twenty-four Evidence records use official Google Cloud, Google Analytics Help and Google Developers
documentation. They were verified on 2026-07-13 and 2026-07-14 for mutable platform boundaries.

# Platform architecture

BigQuery is a fully managed serverless analytical platform with independent storage and compute.
Projects contain datasets; datasets contain tables and views. Dataset location is immutable after
creation, and referenced datasets must be location-compatible. IAM roles govern users, groups and
service accounts through inherited and resource-level permissions.

# Billing and cost controls

Compute is available through on-demand processing and capacity reservations. Dry runs estimate bytes
before execution. Maximum-bytes-billed and quotas reduce uncontrolled on-demand cost. These controls
do not replace table design: partition pruning, clustering block pruning and restricted projections
remain essential for recurring workloads.

# GA4 export lifecycle

A linked GA4 property exports to `analytics_<property_id>`. Daily mode creates
`events_YYYYMMDD`; streaming mode uses temporary `events_intraday_YYYYMMDD`. Daily tables can be
restated for up to three days by late-arriving events, while events arriving after that documented
window are excluded from export. Intraday tables omit some daily-only user and acquisition fields.

# Export schema and grain

The exported row grain is an event. Nested and repeated structures include event parameters, user
properties and items. Consent state is stored in `privacy_info`. Collected traffic-source fields and
session-attributed traffic-source records have different meanings. Ecommerce analysis must separate
event, transaction and item grain.

# SQL reconstruction

Wildcard date ranges use `_TABLE_SUFFIX`; repeated records require typed extraction from `UNNEST`.
Event counts count rows. User counts depend on the identity key. Sessions commonly combine
`user_pseudo_id` with `ga_session_id`. Distinct transactions should use `transaction_id` where
purchase-event duplication is possible. Purchase and refund logic requires explicit event filters,
fields, currencies and signs.

# Reporting parity boundary

BigQuery is not a byte-for-byte or metric-for-metric replica of GA4 reports. GA4 reporting identity,
modeled data, data-driven attribution, thresholding and interface-specific processing are not
implicitly reproduced in exported event SQL. Any comparison requires aligned identity, attribution,
time zone, late-arrival, deduplication and currency rules.

# Retention and recovery

Time travel defaults to seven days and is configurable between two and seven days. A separate
seven-day fail-safe follows, but it is not directly queryable by users. Table snapshots provide a
read-only point-in-time preservation mechanism beyond time travel. Dataset, table and partition
expiration must be designed together because table expiration takes precedence.

# Optimization

Partition filters enable partition pruning. Filters on clustered columns enable block pruning.
Partitioning and clustering can be combined, but optimization depends on workload shape, data volume
and filter patterns rather than a universal schema prescription.

# Transformations

Scheduled queries execute GoogleSQL and can populate destination tables using scheduled-time
parameters. Logical views evaluate their defining query at read time. Supported materialized views
persist derived results and can maintain them incrementally. These surfaces support a layered path
from raw GA4 export through normalized events, sessions, transactions and reporting marts.

# Governance

Row access policies restrict visible rows. Policy tags protect columns and require both dataset and
tag permissions. BigQuery Admin Activity and Data Access audit logs record supported administrative,
read and write operations. Governance therefore combines IAM, row rules, column rules, logging,
retention and cost controls.

# Recommended warehouse layers

The evidence supports a four-layer analytical design: raw exported events; normalized typed events;
reconstructed sessions, users, transactions and items; and governed marts or materialized outputs.
This is a recommendation derived from the documented capabilities, not a canonical Fact.

# Open questions

Mutable pricing, quotas, editions, materialized-view compatibility, row-level-security interactions,
export schema additions and GA4 processing differences require periodic verification. Production
identity, attribution, consent and currency policies remain implementation-specific.
