# Repository Quality Gates

## Purpose

This document defines the minimum conditions for considering research, maintenance, documentation, and Pull Requests complete.

## Definition of done for canonical research

A canonical research block is complete only when:

- the scope is explicit in `STATE.md`;
- relevant existing entities were checked for duplicates;
- official Evidence was collected;
- every confirmed Fact has supporting Evidence;
- Facts are atomic and correctly scoped;
- IDs were generated by repository tooling;
- all cross-references resolve;
- mutable claims include verification dates;
- unresolved conflicts are recorded as risks or open questions.

## Definition of done for a phase

A phase is complete only when:

- all approved research blocks are complete;
- required Evidence and Fact packages exist;
- missing reusable Concepts were added only where justified;
- the final View exists and validates;
- the final Report exists and validates;
- `STATE.md` accurately records completion;
- `INDEX.jsonl` is regenerated;
- acceptance tests match the intentional production inventory;
- no temporary workflows or diagnostics remain;
- all local checks pass;
- CI is green;
- the PR is reviewed, marked Ready, and merged.

## Definition of done for documentation-only work

Documentation-only work is complete when:

- content is consistent with canonical architecture and current state;
- no canonical claims are introduced without references;
- links and file names are correct;
- Markdown structure is readable;
- all automated checks pass;
- `INDEX.jsonl` remains unchanged unless indexed front matter changed.

## Mandatory validation suite

Run from repository root:

```bash
python scripts/validate_knowledge.py
python scripts/validate_links.py
python scripts/validate_markdown_frontmatter.py
python scripts/generate_index.py
python scripts/generate_index.py --check
pytest
ruff check .
mypy scripts
```

No check may be skipped in the final validation run without an explicit documented exception.

## Quality dimensions

### Traceability

Every confirmed claim must be traceable from Fact to Evidence.

Failure examples:

- missing Evidence ID;
- Evidence points to an unrelated source;
- source summary overstates the documentation;
- report prose contains the only copy of an important claim.

### Atomicity

Facts must be independently maintainable.

Failure examples:

- one Fact combines a limit, a delay, and a permission rule;
- one statement mixes current behavior with a recommendation;
- one object contains unrelated product surfaces.

### Scope correctness

Claims must identify conditions that materially affect interpretation.

Check:

- product edition;
- platform;
- channel;
- geography;
- time period;
- processing surface;
- verification date.

### Source quality

Prefer official primary documentation. Third-party context must not replace available official sources for confirmed product behavior.

### Structural integrity

Check:

- schema validity;
- unique IDs;
- valid typed prefixes;
- package size limits;
- resolvable references;
- generated index freshness;
- valid View and Report front matter.

### Projection integrity

Views and Reports must remain projections over canonical knowledge.

A projection fails quality review when it:

- introduces unsupported facts;
- contradicts selected Facts;
- hides limitations;
- omits important scope;
- presents dated analysis as timeless truth.

### Repository hygiene

Final branches must not contain:

- temporary workflows;
- debug logs;
- generated artifacts not owned by the project;
- commented-out validation;
- unrelated refactors;
- duplicate stale files;
- secrets or credentials.

## Pull Request readiness checklist

Before marking Ready:

- [ ] Scope is complete.
- [ ] PR body reflects actual state.
- [ ] `STATE.md` is current.
- [ ] Required View and Report are present.
- [ ] IDs and references were checked.
- [ ] `INDEX.jsonl` is current.
- [ ] Temporary files were removed.
- [ ] Full validation suite passes.
- [ ] GitHub Actions is green.
- [ ] Diff contains no unrelated changes.
- [ ] Open questions and risks are documented.

## Merge checklist

Before merge:

- [ ] PR is not Draft.
- [ ] Required checks are successful.
- [ ] Head SHA matches the validated commit.
- [ ] Merge strategy is appropriate.
- [ ] No newer unvalidated commit exists.

After merge:

- [ ] Confirm the PR is merged.
- [ ] Confirm `main` contains the expected state.
- [ ] Close stale duplicate PRs.
- [ ] Move to the next explicit phase or maintenance state.

## Severity model

### Blocking

- schema errors;
- broken references;
- duplicate IDs;
- confirmed Facts without Evidence;
- stale generated index;
- failed tests or CI;
- secrets or real user data;
- unresolved merge conflicts.

### Non-blocking but required to record

- source ambiguity;
- mutable behavior that needs later re-verification;
- incomplete coverage outside approved scope;
- product documentation conflicts;
- recommendations not yet validated as implementation guidance.

## Quality review questions

A reviewer or agent should ask:

1. Is every important statement located in the correct entity type?
2. Can each confirmed Fact be independently verified?
3. Is any existing knowledge duplicated?
4. Are mutable claims correctly dated and scoped?
5. Does the View help navigation without creating hidden truth?
6. Does the Report explain limitations and open questions?
7. Is the repository clean and reproducible?
8. Would another agent understand the next step from `STATE.md` alone?

## Completion rule

A task is not complete because files were created. It is complete only when the repository is coherent, validated, indexed, reviewable, and merged according to the approved scope.
